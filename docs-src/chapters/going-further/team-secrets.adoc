[#team-secrets]
== Team Secrets with `sops`

The plain credentials file (<<credentials>>) covers a personal secret -- your own tokens, your own
keys. This chapter is for the other case: a genuinely *shared team secret* that needs field-level
encryption at rest, not just ordinary file permissions.

NOTE: Most people don't need this. It's an advanced, opt-in path (`workspacesHost.secrets` in
`home/secrets.nix`) for the specific case the plain credentials file doesn't cover.

=== How it works

Each secret you declare is decrypted at *activation* time (every `home-manager switch`, never at
build/eval time) into `$XDG_STATE_HOME/workspaces-host/secrets/`, so the plaintext never lands in
the world-readable Nix store. This module intentionally does not manage decryption key material
itself -- provisioning the key is a deliberate, separate, human action (Constitution Principle III),
the same category as a git identity or an API key.

[mermaid]
....
sequenceDiagram
  participant Author
  participant Repo as Git repo
  participant Machine as Your machine
  participant Wrapper as Credential wrapper
  Author->>Author: sops --encrypt
  Author->>Repo: commit secrets/*.enc.yaml
  Machine->>Repo: pull
  Machine->>Machine: home-manager switch (activation)
  Machine->>Machine: decrypt into $XDG_STATE_HOME/.../secrets/
  Wrapper->>Machine: read plaintext, per invocation only
....

=== Declaring one

In `~/.config/workspaces-host/local.nix` (<<local-nix>>):

[source,nix]
----
{ ... }:
{
  workspacesHost.secrets."github-token" = {
    sopsFile = ./secrets/github-token.enc.yaml;
    path = "env/GITHUB_TOKEN";
  };
}
----

`sopsFile`:: the path to a `sops`-encrypted file.
`path`:: where the decrypted plaintext is written, relative to
`$XDG_STATE_HOME/workspaces-host/secrets` -- the same directory the plain credentials mechanism
writes into, so any tool that already reads from there (the AI-CLI credential wrappers, for
instance) picks it up identically.
`extractKey` (optional, defaults to `"data"`):: `sops --encrypt` wraps unstructured input under a
`data` key by convention; set this to `null` if the encrypted file is a real multi-key document and
you want the raw decrypted output instead of one extracted field.

=== Creating the encrypted file itself

[source,shell]
----
$ age-keygen -o ~/.config/sops/age/keys.txt       # once, if you don't have an age key yet
$ AGE_PUBLIC_KEY=$(grep "public key:" ~/.config/sops/age/keys.txt | awk '{print $NF}')
$ echo '{"data": "the-real-secret-value"}' > plain.json
$ sops --encrypt --age "$AGE_PUBLIC_KEY" --input-type json --output-type yaml plain.json > secrets/github-token.enc.yaml
$ rm plain.json
----

`sops` and `age` are both installed automatically once you declare at least one secret -- nothing
extra to install by hand. Verify it decrypts correctly before committing it:

[source,shell]
----
$ sops --decrypt --extract '["data"]' secrets/github-token.enc.yaml
the-real-secret-value
----

The encrypted file (`*.enc.yaml`) is safe to commit -- that's the whole point of encrypting it at
rest. Never commit the age private key (`~/.config/sops/age/keys.txt`) or the plaintext.

=== Applying it

[source,shell]
----
$ workspaces-host-update
----

Same command as everything else. The decrypted value lands at
`~/.local/state/workspaces-host/secrets/env/GITHUB_TOKEN` and is picked up by the same
per-invocation credential wrappers every other secret in this repository uses -- it's never
exported as an ambient shell variable. <<why-secret-scoping>> explains why that matters.
