[#container-ci]
== Container and CI Parity

Both this repository's container images and its CI checks build from the exact same evaluated
home-manager configuration as your host profile -- not a hand-maintained Dockerfile or CI script
that could quietly drift from what you actually run day to day. That's Constitution Principle IV:
container and cloud-harness parity is required, not optional.

[mermaid]
....
flowchart TD
  Flake["flake.nix<br>(one evaluated config)"] --> Host["your host profile"]
  Flake --> Image["oci-image<br>(base + fish)"]
  Flake --> Press["oci-image-press<br>(+ press persona)"]
  Flake --> Rust["oci-image-rust<br>(+ rust persona)"]
  Flake --> Sandboxed["oci-image-sandboxed<br>(+ firewall, non-root)"]
  Flake --> CI["CI checks"]
....

=== Building the container images

[source,shell]
----
$ nix build .#oci-image             # same shell/tools/dotfiles as the host profile
$ docker load < result
$ docker run -it workspaces-host:latest

$ nix build .#oci-image-sandboxed   # + default-deny network egress allowlist, non-root user
$ nix build .#oci-image-press       # + the press persona (AsciiDoc/LaTeX/EPUB typesetting)
$ nix build .#oci-image-rust        # + the rust persona (Rust + native C/CMake toolchain)
----

The sandboxed variant runs `init-firewall` as root, verifies its own allowlist, then drops to a
non-root user before handing off to the workload -- the shape you'd actually want for an
autonomous AI-agent session with no human watching each command.

=== Pulling the published image instead of building it

Because this repository is public, a GitHub Actions workflow (`.github/workflows/container-image.
yml`) publishes three images to the GitHub Container Registry on every push to `main` that touches
`home/`, `pkgs/`, `oci/`, or the flake itself: `workspaces-host-v3` (base + fish),
`workspaces-host-v3-press` (the same, plus the `press` persona -- <<personas>> -- for AsciiDoc/
LaTeX/EPUB typesetting), and `workspaces-host-v3-rust` (the same, plus the `rust` persona -- a
stable Rust toolchain and the native C/CMake toolchain its heaviest crate graphs need) -- each its
own image, so pulling the base one never costs you a TeX Live or Rust-toolchain download. Each gets
a `latest` tag and a `sha-<short-sha>` tag for pinning to an exact build. Running the workflow by
hand on another branch publishes only that commit's `sha-` tag, so you can pin and test a change
before it merges without moving `latest` for everyone. Pulling any of them skips
the Nix build (and the git clone) entirely:

[source,shell]
----
$ docker pull ghcr.io/intellectual-frontiers/workspaces-host-v3:latest
$ docker run -it ghcr.io/intellectual-frontiers/workspaces-host-v3:latest

$ docker pull ghcr.io/intellectual-frontiers/workspaces-host-v3-press:latest
$ docker pull ghcr.io/intellectual-frontiers/workspaces-host-v3-rust:latest
----

All three images publish for `linux/amd64` and `linux/arm64` from the same workflow run, as a
single multi-arch tag each -- `docker pull` picks the architecture matching your own machine
automatically, no `--platform` flag needed. This matters in practice: a non-technical engineer on
an Apple Silicon Mac gets a native arm64 image, not an amd64 one running under slow emulation.

This is for exactly the two audiences "ease testing" implies: a human who wants to try this
environment or test a change without installing Nix first, and an AI agent that wants a disposable
sandbox already matching this repository's exact tool versions:

[source,shell]
----
$ docker run --rm ghcr.io/intellectual-frontiers/workspaces-host-v3:latest doctor --all
----

Each image has a minimal `/etc/os-release` (and the same file at `/usr/lib/os-release`):
`ID=workspaces-host`, `VERSION_ID` set to the short commit it was built from (the same commit its
`sha-` tag names), and `VARIANT_ID` set to `base`, `press`, or `rust`. The devcontainer CLI and VS
Code both read it. It claims no `ID_LIKE` on purpose: there's no `apt` or `apk` in here, and a
devcontainer feature that thinks there is fails worse than one that doesn't recognize the OS.
`doctor` reads it too: inside an image, a missing `nix` is a `WARN` (the image ships the profile's
closure, not Nix), not the `FAIL` it is on a host.

=== Opening this repository as a devcontainer

`.devcontainer/devcontainer.json` at the repository root points its `image` property at the same
published tag, so VS Code, GitHub Codespaces, or the standalone `devcontainer` CLI all pick it up
with zero configuration -- "Reopen in Container" (or its Codespaces equivalent) is the entire
setup step, no Nix install, no local build:

[source,shell]
----
$ npx @devcontainers/cli up --workspace-folder .
----

It sets `remoteUser`/`workspaceFolder` explicitly (the image itself defines neither a non-root
user nor a devcontainer-shaped working directory -- that's deliberately kept out of `oci/
default.nix`, which stays focused on being a plain, correct OCI image) and runs `doctor` via
`postCreateCommand` through a login shell, so you see an authoritative health check the moment the
container is up.

Want this same environment as the devcontainer for a *different* project, not this repository?
Copy the `image` line into that project's own `.devcontainer/devcontainer.json` -- there's nothing
else to add.

Prefer fish? `.devcontainer/fish/devcontainer.json` opens the exact same published image -- no
second image to build or publish -- and just sets the devcontainer's own default shell to fish
(`remoteEnv.SHELL` plus VS Code's own terminal-profile setting). The image already has fish: the
published image is built from the base profile plus the `fish` persona (<<personas>>), purely
additive like every persona, so nothing about the default (bash) devcontainer changes. Pick it
explicitly with the CLI's `--config` flag:

[source,shell]
----
$ npx @devcontainers/cli up --workspace-folder . --config .devcontainer/fish/devcontainer.json
----

A real host install still only gets fish through `ws-persona activate fish` (<<personas>>) -- this
is purely about which shell a devcontainer opens into, not a second way to turn fish on.

=== `ws-start`: the first thing another repository's devcontainer should run

Every Intellectual Frontiers repository is moving to the same rule this one already follows: no
`make install`, no setup step, after cloning -- in every flavor (bare-metal Linux, a Linux VM
including WSL, this published image, a devcontainer, a cloud agent session). Each IF repository
carries its own `.devcontainer/devcontainer.json` pointing at an image this flake publishes, plus
its own `.devcontainer/ws-repos.json` (exactly the format `ws-repos` already reads -- <<repos>>).

`ws-start` is the one command that turns "the container exists" into "logged in and every repo
cloned." It belongs in `postAttachCommand`, never `postCreateCommand`: creating a container happens
before anyone has attached to it, so there's no GitHub login yet to clone a private repo with.
`ws-start`:

1. Checks `gh auth status`. If you're not logged in, it runs `gh auth login` -- the device-code
   flow works the same way in a plain terminal, VS Code's integrated terminal, and a Codespace (a
   Codespace already has a token, so this step is instant there). Once authenticated, it runs `gh
   auth setup-git` so plain `git clone`/`git push` against github.com use that same login.
2. Runs `ws-repos adopt` on the checkout the editor opened, when that checkout is listed in
   `$WS_REPOS_CONFIG` but isn't under `~/workspaces` -- always the case in a Codespace or a volume
   devcontainer, which open `/workspaces/<repo>`. `~/workspaces/<host>/<org>/<repo>` becomes a link
   to it and every other listed repo gets a link beside it, so `../.github` resolves (<<repos>>).
3. Runs `ws-repos ensure`, honoring `$WS_REPOS_CONFIG` exactly as `ws-repos` already does on its
   own -- nothing new to configure in `ws-start` itself.

It's idempotent: attach again, and every step is a near-instant no-op. Clones never stop at a
username prompt (`GIT_TERMINAL_PROMPT=0`): a private repo before login fails at once with git's own
reason. It never rebases, merges, or stashes anything: the checkout you opened is only fetched,
and a repo with uncommitted changes or diverged local commits is left as it was and named in the
summary as "not updated". If any repo failed, the closing summary names each one and `ws-start` exits non-zero; when
login didn't complete, it says that `gh auth login` and then `ws-start` is the fix. A different IF
repository's own `devcontainer.json` copies this pattern directly:

[source,json]
----
{
  "image": "ghcr.io/intellectual-frontiers/workspaces-host-v3:latest",
  "remoteUser": "root",
  "workspaceFolder": "/workspaces/${localWorkspaceFolderBasename}",
  "remoteEnv": {
    "WS_REPOS_CONFIG": "/workspaces/${localWorkspaceFolderBasename}/.devcontainer/ws-repos.json"
  },
  "postAttachCommand": "bash -lc 'ws-start'"
}
----

=== Using it in a real pipeline

Because the image is built from the same flake output as `homeConfigurations.default`, a CI job
that builds `.#oci-image` and runs your test suite inside it is testing the same tool versions,
the same shell, the same everything an engineer's machine has -- not a parallel environment that
happens to be close enough. A minimal pipeline step:

[source,shell]
----
$ nix build .#oci-image
$ docker load < result
$ docker run --rm workspaces-host:latest sh -c 'cd /workspace && your-test-command'
----

=== Validating a change before you call it done

[source,shell]
----
$ nix flake check --all-systems              # evaluates + builds the base activation, every system
$ nix build ".#homeConfigurations.default.activationPackage"
$ nix build ".#homeConfigurations.current-backend.activationPackage" --impure
----

`nix flake check` evaluating cleanly is not the same claim as "activation actually works" -- for a
real change to `home/` or a persona, also do a scratch-`$HOME` activation and run `doctor --all`
against it, expecting zero unexpected `FAIL`s. This is exactly what the repository's own CI
workflow does on every push and pull request.
